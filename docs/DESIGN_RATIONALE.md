# CO·XING QuestMarker — Design Rationale

> 현실 기물을 가상 콘텐츠의 조작 인터페이스로 활용하는 XR 저작 방식 탐구

CO·XING QuestMarker는 ‘어떻게 하면 XR 공간에서 더 직관적으로 장면을 편집할 수 있을까?’라는 질문에서 출발했다. 현실의 기물에 3D 오브젝트를 대응시키고, 기물의 위치와 방향을 바꾸는 행동을 가상 장면 구성의 입력으로 활용하고자 한다.

현재 공개본은 이 방향을 탐색하기 위한 물리–가상 매핑 프로토타입의 선별 코드와 문서다. 완성된 XR 편집기나 사용성 검증 결과를 의미하지 않는다. 개발 기준 상태는 2025-12-13이며, 이 문서는 2026-11-26 공개 자료와 기획 의도를 바탕으로 작성했다. [저장소 README](https://github.com/Kyojunnn/coxing-questmarker-portfolio/blob/main/README.md)

## 1. 디자인 동기와 질문

XR 장면을 연출하려면 머릿속의 공간 관계를 위치·회전 값이나 편집 도구의 조작으로 옮겨야 한다. CO·XING은 이 변환 과정의 부담을 줄이고, 창작자가 대상의 배치와 관계에 집중할 수 있는 제작 경험을 지향한다.

여기서 주목한 행동은 인형놀이처럼 물건을 놓고, 돌리고, 서로 가까이 옮기는 일이다. 현실 기물이 가상 캐릭터의 조작 대상이 된다면, 창작자는 물리적 위치와 방향을 통해 장면 의도를 표현할 수 있다.

**디자인 질문은 “현실 기물을 움직이는 익숙한 행동이 XR 장면의 위치·회전 편집을 더 이해하기 쉽고 통제하기 쉽게 만들 수 있는가?”이다.** 직관성 향상은 현재의 결론이 아니라 앞으로 검증할 가설이다.

## 2. ‘무엇을–언제–어떻게’에서의 위치

CO·XING의 인터랙션 구상을 다음과 같이 정리할 수 있다. 아래 예시는 프레임워크 설명을 위한 기획 예시이며, 데모에서 실행되는 시나리오가 아니다.

| 구분 | 창작자의 결정 | 예시 | QuestMarker와의 관계 |
|---|---|---|---|
| 무엇을 | 어떤 대상과 사건을 만들 것인가 | 캐릭터와 문을 장면에 배치한다 | 마커와 콘텐츠의 연결이 대상 구분의 기반이 된다 |
| 언제 | 어떤 조건에서 사건이 일어나는가 | 사용자가 문에 접근하면 반응한다 | 조건·트리거 저작 기능은 현재 확인 범위에 없다 |
| 어떻게 | 의도한 배치와 반응을 어떻게 구성·조정하는가 | 캐릭터를 옮기고 방향을 바꿔 연출한다 | 이번 프로토타입이 집중하는 물리적 편집 입력이다 |

QuestMarker는 특히 **‘어떻게’ 단계의 입력 방식**을 탐구한다. 기물과 가상 오브젝트의 위치·회전을 연결하는 것이 현재의 기술적 범위이며, 동작·사건·타임라인까지 편집하는 전체 저작 흐름은 후속 과제다.

## 3. 현실 기물을 편집 인터페이스로 선택한 이유

현실 기물은 손으로 잡을 수 있는 형태와 접촉감을 제공한다. 이를 가상 오브젝트의 대리물로 사용하면, ‘이 물건을 움직이면 저 캐릭터가 움직인다’는 대응을 통해 공간 조작을 설명할 수 있다는 가설을 세웠다. 여러 기물에 서로 다른 콘텐츠를 연결하면 대상 간 거리와 방향도 물리적으로 구성할 수 있다.

단, **손으로 물건을 움직이는 것과 시스템이 손을 추적하는 것은 별개**다. 이 접근에서 시스템의 입력은 손동작 자체가 아니라 카메라에서 관측한 마커의 자세다. 또한 임의의 물체를 인식해 자동으로 3D 모델을 입히는 방식이 아니라, 마커 ID에 미리 연결한 오브젝트를 표시하는 구조다. [프로젝트 개요](https://github.com/Kyojunnn/coxing-questmarker-portfolio/blob/main/docs/PROJECT_OVERVIEW.md)

## 4. 프로토타입의 기술적 접근

공개 코드에서 확인되는 처리 흐름은 다음과 같다.

```text
Quest 카메라 영상과 카메라 파라미터
  → 영상 축소·변환 및 ArUco 마커 검출
  → 마커 코너와 실제 크기를 이용한 solvePnP 자세 추정
  → Unity 좌표 변환 및 위치·회전 보간
  → 카메라의 월드 변환과 결합
  → 마커 ID에 연결된 3D 오브젝트의 Transform 갱신
```

`ArUcoTrackingAppCoordinator`는 카메라 권한·영상 준비 대기, 마커 ID와 GameObject의 연결, 표시 모드 전환을 담당한다. `ArUcoMarkerTracking`은 OpenCVForUnity를 사용한 검출·자세 추정과 오브젝트 갱신, 검출 상태에 따른 스케일 등장·퇴장 처리를 포함한다. 초기 화면은 카메라 디버그 뷰이며 A 버튼으로 표시 모드를 전환하는 코드가 있다. [Coordinator 코드](https://github.com/Kyojunnn/coxing-questmarker-portfolio/blob/main/src/ArUcoTrackingAppCoordinator.cs), [Tracking 코드](https://github.com/Kyojunnn/coxing-questmarker-portfolio/blob/main/src/ArUcoMarkerTracking.cs)

저장소의 보존 개발본 검토 기록에는 Unity 6000.2.4f1, Quest 3/3S 대상 설정, ID 0/1의 콘텐츠 연결이 명시되어 있다. 씬·프리팹·모델·SDK·플러그인은 공개본에 포함되지 않아, 선별 코드만으로 해당 구성을 재현하거나 빌드할 수 없다. [기술 구조](https://github.com/Kyojunnn/coxing-questmarker-portfolio/blob/main/docs/TECHNICAL_ARCHITECTURE.md)

카메라·검출 기반은 Takashi Yoshinaga의 QuestArUcoMarkerTracking과 Meta 카메라 샘플에 기반한다. 이 프로젝트의 디자인적 초점은 그 기반을 기물–콘텐츠 연결과 장면 구성 경험에 활용하는 데 있다. 기반 기술 전체를 독자 구현한 것으로 설명하지 않으며, 변경별 작성자와 시점 전체도 복원되어 있지 않다. [출처 고지](https://github.com/Kyojunnn/coxing-questmarker-portfolio/blob/main/THIRD_PARTY_NOTICES.md), [프로젝트 개요](https://github.com/Kyojunnn/coxing-questmarker-portfolio/blob/main/docs/PROJECT_OVERVIEW.md)

## 5. 주요 디자인 결정과 트레이드오프

아래는 현재 구조를 디자인 목표에 비추어 정리한 판단이다. 효과는 실행·사용자 평가로 확인해야 한다.

| 결정 | 디자인적 이유 | 감수해야 할 제약 |
|---|---|---|
| 마커 ID와 콘텐츠를 명시적으로 연결 | 조작 대상과 가상 결과의 대응을 단순하게 만든다 | 마커 부착·사전 설정이 필요하고 임의 물체 인식은 제공하지 않는다 |
| 기물의 위치·회전을 가상 오브젝트에 반영 | 물리적 움직임을 공간 배치 입력으로 활용한다 | 마커 크기, 좌표축, 모델 피벗과 오프셋이 체감 정합에 영향을 준다 |
| 위치·회전 보간 사용 | 자세 변화의 떨림을 완화하려는 처리다 | 추종 지연과 정밀 조작 사이의 균형을 측정해야 한다 |
| 검출 상태에 스케일 등장·퇴장 연결 | 콘텐츠의 등장과 소실을 연출하는 구조다 | 연출만으로 추적 상태를 명확히 전달하는지는 미확인이다 |
| 디버그 뷰와 콘텐츠 표시 분리 | 검출 결과와 콘텐츠 표시를 점검할 수 있다 | 숨김 상태를 검출 실패로 오해하지 않도록 피드백을 설계해야 한다 |

보간과 등장·퇴장 코드의 존재는 확인되지만, 떨림 감소나 자연스러운 전환이 실기기에서 달성됐다는 뜻은 아니다. [기술 구조](https://github.com/Kyojunnn/coxing-questmarker-portfolio/blob/main/docs/TECHNICAL_ARCHITECTURE.md)

## 6. 구현 근거와 검증 경계

| 구분 | 현재 설명할 수 있는 범위 |
|---|---|
| 공개 소스에서 정적 확인 | 카메라 준비 대기, ID 매핑, ArUco 검출·자세 추정, 위치·회전 보간, Transform 갱신, 스케일 등장·퇴장 코드 경로 |
| 저장소 문서의 보존본 검토 기록 | ID 0/1의 서로 다른 콘텐츠 연결, 씬·UI 구성과 개발 환경 설정. 해당 씬을 이 문서 작성 과정에서 직접 검토한 것은 아니다 |
| 실행 미검증 | 공개 준비 및 이 문서 작성 과정에서 Unity 컴파일·Android 빌드·Quest 실행 미수행. 추적 안정성, FPS, 지연, APK와 소스 일치 미확인 |
| 구현 근거 미확인 | Unity 손 추적, 가상 Grab, 영구 공간 앵커, AI 의도 해석·콘텐츠 편집, 완성된 XR 저작 도구 |
| 디자인 가설 | 조작 학습 부담 감소, 배치 의도 전달의 용이성, 창작자의 통제감 향상 |

현재 자료에는 시연 영상이나 성능·사용성 측정 결과가 없다. 따라서 ‘직관적인 편집을 구현·검증했다’보다 **‘직관적인 편집 입력을 탐구하기 위해 물리–가상 매핑 코드 경로를 구성했다’**는 설명이 적절하다. [구현 상태](https://github.com/Kyojunnn/coxing-questmarker-portfolio/blob/main/docs/IMPLEMENTATION_STATUS.md)

## 7. 위험과 평가 기준

마커가 가려지면 이동한 기물의 위치를 계속 알아낼 수 없다. 특히 현재 코드는 검출 코너가 0개일 때 조기 반환하여 소실 타이머와 퇴장 갱신을 건너뛸 수 있다. 이는 정적으로 확인한 결함 후보이며, 재현·수정 완료 항목이 아니다. [문제 해결 및 재현 계획](https://github.com/Kyojunnn/coxing-questmarker-portfolio/blob/main/docs/TROUBLESHOOTING.md)

아래 항목은 향후 평가 계획이다. 아직 통과 결과나 목표 성능 달성을 주장하지 않는다.

| 위험·질문 | 평가 방법 | 기록할 기준 |
|---|---|---|
| 가림·시야 이탈 시 편집 상태를 이해할 수 있는가 | 한 마커 소실, 전체 소실, 재등장을 각각 시험 | 잘못 남는 표시, 퇴장·복원 상태, 재검출 시간 |
| 물리–가상 정합이 조작을 방해하는가 | 고정 위치와 알려진 이동·회전 조건에서 비교 | 위치·회전 오차, 정지 시 떨림, 추종 지연 |
| 환경 변화에도 입력이 유지되는가 | 거리·각도·조명·이동 속도 조건별 반복 | 검출 성공률, 끊김 빈도, ID 혼동 |
| 표시가 자연스럽고 기기 부담이 허용 가능한가 | 동일 장면에서 표시 모드·설정별 비교 | FPS, CPU/GPU 시간, 장시간 실행 상태 |
| 기물 조작이 실제로 편집 부담을 줄이는가 | 동일한 배치·방향 맞추기 과제를 기존 위치·회전 조작 방식과 비교 | 완료 시간, 배치 오차, 수정 횟수, 도움 요청, 주관적 통제감 |
| 대상과 상태를 이해하기 쉬운가 | 처음 사용하는 참여자가 대상 선택·소실·재등장 상황을 설명하도록 관찰 | 대응 관계 이해, 상태 오해, 학습 과정 |

성능 측정은 기기·OS·빌드·카메라 조건을 기록하고, 사용성 비교는 과제 난이도와 연습량을 맞춰 진행한다. 허용 오차와 성공 기준은 예비 측정 후 본 평가 전에 정한다. 물건을 들고 조작할 때의 피로, 마커 가림, 제한된 물리 작업 공간도 관찰한다.

## 8. 로드맵과 미래 저작 경험

1. **기준 동작 복원:** 의존성·씬 연결·권한·빌드 대상을 복원하고, 컴파일·빌드·실기기 결과를 기록한다. ID 0/1의 단독·동시 표시와 이동·회전을 확인한다.
2. **소실·재등장 처리 검증:** 전체 검출 소실을 재현하고 상태 갱신을 수정한다. 부분 소실과 전체 소실을 구분해 회귀 확인한다.
3. **측정 기반 안정화:** 지연·떨림·검출률의 기준값을 확보한 뒤, 중복 검출·디버그 복사·할당 비용과 보간·해상도 설정을 한 번에 하나씩 비교한다. API 전환만으로 성능 향상을 가정하지 않는다.
4. **저작 흐름 확장과 사용성 평가:** 배치 확정·해제, 되돌리기, 저장·재현 등 편집 상태를 설계하고 기물 조작 방식의 효용을 평가한다. 이는 현재 완료된 기능이 아니다.
5. **AI 기반 저작과 체험 중심 편집 탐구:** 창작자가 자연어와 공간 행동으로 의도를 전달하면 AI가 대상·조건·반응을 제안하고, 창작자가 XR에서 체험하며 수정하는 흐름을 검토한다.

1–3단계는 저장소의 [개발 재개 계획](https://github.com/Kyojunnn/coxing-questmarker-portfolio/blob/main/docs/REDEVELOPMENT_ROADMAP.md)에 따른다. 4–5단계는 디자인 확장 방향이다.

장기적으로 지향하는 흐름은 **의도 표현 → 구성 제안 → XR 체험 → 피드백 → 수정**이다. AI가 제안한 ‘무엇을–언제–어떻게’를 창작자가 확인·수정할 수 있도록 통제권과 되돌리기를 함께 설계해야 한다. 특정 생성형 모델 연동, 공간 자동 생성, 손 추적 편집이 현재 구현됐다는 뜻은 아니다.

QuestMarker의 현재 역할은 이 미래 경험에 필요한 입력 중 하나, 즉 **현실의 움직임을 가상 장면의 위치·회전에 연결하는 기반**을 탐색하는 데 있다.
